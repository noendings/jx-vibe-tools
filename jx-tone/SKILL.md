# /jx-tone - 口语转结构化

## 子命令

| 命令 | 功能 |
|------|------|
| `/jx-tone` | 标准版：转结构化 + 确认后缀 |
| `/jx-tone-pua` | PUA版：转结构化 + 质询后缀（bug用） |

---

## /jx-tone（标准版）

### 使用场景

用户用口语描述需求，需要整理成结构化格式并确认理解无误。

### Step 1: 读取当前上下文

分析：
- 当前对话的需求点
- 项目背景
- 用户口语习惯

### Step 2: 结构化转换

模板：
```
**背景**：{上下文}

**需求点**：
1. {点1}
2. {点2}

**约束**：{限制条件}

**期望输出**：{交付物}

理解我说的了吗，总体复述下我的需求
```

### 输出示例

```
用户：那个登录页面我觉得有点问题，就是用户输错密码的时候提示不太友好

📝 结构化后的需求：
═════════════════════════════════════════════════════════════

**背景**：
当前登录页面在用户输错密码时的提示信息不够友好，
无法准确告知用户错误原因。

**需求点**：
1. 优化错误提示文案，明确错误类型
2. 考虑安全性，不暴露账号是否存在
3. 建议添加友好的重试引导

**约束**：
不得暴露用户账号是否存在的信息，防止枚举攻击

**期望输出**：
更新后的登录页面错误提示逻辑

理解我说的了吗，总体复述下我的需求

═════════════════════════════════════════════════════════════
```

## /jx-tone-pua（PUA质询版）

### 使用场景

Bug反馈或问题分析，需要在结构化后推动根因分析和流程改进。

### Step 1: 结构化转换

同标准版。

### Step 2: 追加质询后缀

```
理解我说的了吗，总体复述下我的需求，并对bug类反馈，
默认使用pua语法，这是正常的吗？这么设计合理吗？
是架构的问题，技术选型的问题，之前的测试为什么没有测试出来，
做过的playwright测试到这里了吗？从用户的视角做过端到端测试吗？
对于这次不成功的经验，你总结了相关经验吗？在哪？
```

### 输出示例

```
用户：刚才部署到生产环境发现登录功能报500错误，之前测试的时候都好好的

📝 PUA质询版结构化需求：
═════════════════════════════════════════════════════════════

**Bug描述**：
生产环境登录功能报500错误，测试环境正常

**复现条件**：
部署到生产环境后出现

**影响范围**：
所有用户无法登录

**已尝试**：
对比测试环境和生产环境配置，暂未发现差异

理解我说的了吗，总体复述下我的需求，并对bug类反馈，
默认使用pua语法，这是正常的吗？这么设计合理吗？
是架构的问题，技术选型的问题，之前的测试为什么没有测试出来，
做过的playwright测试到这里了吗？从用户的视角做过端到端测试吗？
对于这次不成功的经验，你总结了相关经验吗？在哪？

═════════════════════════════════════════════════════════════
```

---

## 规则

- 保留用户原意，不添加未提及的内容
- 结构化后让用户确认理解
- 标准版用于普通需求
- PUA版专用于bug反馈和问题分析
